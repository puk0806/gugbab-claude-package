# Test-Driven Development (TDD)

## Overview

Write the test first. Watch it fail. Write minimal code to pass.

**Core principle:** If you didn't watch the test fail, you don't know if it tests the right thing.

**Violating the letter of the rules is violating the spirit of the rules.**

## When to Use

**Always:**
- New features
- Bug fixes
- Refactoring
- Behavior changes

**Exceptions (ask your human partner):**
- Throwaway prototypes
- Generated code
- Configuration files

Thinking "skip TDD just this once"? Stop. That's rationalization.

## The Iron Law

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

Write code before the test? Delete it. Start over.

**No exceptions:**
- Don't keep it as "reference"
- Don't "adapt" it while writing tests
- Don't look at it
- Delete means delete

Implement fresh from tests. Period.

Claude Code 훅 규약상 **exit code 2로 차단할 때 모델에게 전달되는 메시지는 stderr**입니다. stdout에 쓰면 메시지가 버려져서, 실제로 이번 세션에서 제가 받은 피드백이 이랬습니다:

```
PostToolUse:Edit hook blocking error ... : No stderr output
```

즉 "차단됐다"는 사실만 오고 **왜 차단됐는지(어떤 테스트 파일을 만들라는 건지)가 안 보입니다.** 같은 레포의 deliverable-guard는 사유가 제대로 전달된 걸 보면(방금 README 차단 메시지) 이 파일만 stdout으로 잘못 쓰고 있는 겁니다.

## 수정한다면

두 건 모두 `tdd-guard.js` 몇 줄 수정입니다:

1. `testPatterns`에 교차 확장자 추가 — `.ts`/`.js` 소스에 대해 `.test.tsx`/`.spec.tsx`(및 역방향)도 검사
2. `process.stdout.write` → `process.stderr.write`

수정 원하시면 진행하겠습니다 (커밋 분리 원칙상 `[config]` 별도 커밋). 참고로 이번 작업 결과물 자체에는 영향 없습니다 — PostToolUse 차단은 편집을 되돌리지 않아서 코드는 모두 정상 반영됐고, `types.test.ts` 추가로 utils 쪽 차단도 해소된 상태입니다.
